01

Reuse your working setup

Keep the Lab 5 infrastructure; replace its application entry point.

  1. In STM32CubeIDE, make a separate C++ project for NUCLEO-L433RC-P, named for example PWM. Copying your working ADC project in the IDE is the easiest way to retain its clocks, HAL modules and C++ settings.
  2. Reuse the files in ADC/Core/MyCode, excluding its old Run.hpp and Run.cpp. Add the six supplied files in step 4. The old ADC/LCD/UART classes may remain compiled but are not started by the new Run.
  3. Keep ADC, I2C, UART and TIM HAL modules enabled if all those old classes remain in the build. Otherwise their types can be missing even when the classes are unused.
  4. Keep the Lab 5 80 MHz clock setup. In Clock Configuration, verify APB2 timer clocks = 80 MHz.
If you create a fresh project instead of copying ADC

Use the same board and C++ language. For the clock setup used here: HSI16 → PLL, M = 1, N = 10, R = 2; select PLLCLK for SYSCLK and use AHB/APB1/APB2 divisors of 1. Keep the board's power configuration. Retain Lab 5 peripheral configuration if copying every old class. A fresh STM32 project does not necessarily start at 80 MHz.

Remove the old Run include and old RUN_DESC setup from main.c. Step 4 supplies the replacements.

02

Configure TIM1 in CubeMX

One timer period, three independently adjustable pulse widths.

Select TIM1 → Internal Clock. Enable PWM Generation CH1, CH2 and CH3. Use the normal channels, not the complementary CHxN outputs.

80,000,000 / ((79 + 1) × (999 + 1)) = 1000 Hz. One PWM period is 1 ms, comfortably above the lab's 50 µs minimum.

Connect the RGB LED

Power off while moving wires. Give each colour its own 220 Ω resistor.

Give the PWM pins labels LED_R, LED_G, LED_B. Keep USART1 disabled on PA9/PA10. The default board routes those pins to D1/D0; a modified serial-port solder-bridge configuration can change this. Board routing reference.

If your RGB LED has a common anode instead

Confirm its pinout from its markings or datasheet. Connect the common anode to 3.3 V and set all three PWM channel polarities to Low. Keep the three series resistors. The supplied class still uses 0 = off and 1 = full brightness; do not also invert the values in software. A bare LED's leg order must be checked, not guessed from the module photograph.

Add the six files and connect Run

Save CubeMX and generate code before adding the entry-point call.

  1. Put the six code files in your new project's Core/MyCode. Keep only one Run implementation and one timer period-elapsed callback.
  2. In main.c, replace the old Run include inside USER CODE BEGIN Includes:
#include "../MyCode/Run.h"

Inside USER CODE BEGIN 2, after generated peripheral initialization, replace the old descriptor/call with:

struct RUN_DESC desc = {0};
desc.p_htim_pwm = &htim1;
Run(desc);

Verify CubeMX generated MX_TIM1_Init(); before this block and HAL_TIM_MspPostInit(&htim1) in TIM1 initialization. The latter configures the output pins. If using separate generated tim.c/tim.h files, also include tim.h for htim1.

First build: leave color_cycle_enabled = false in Run.cpp. The three PWM outputs start at zero duty. No LCD, ADC interrupt or old application loop is needed.
05
Required task 1

Change brightness while paused

  1. Start Debug, resume past initialization, then pause inside the empty Task 1 loop.
  2. Open SFRs → TIM1. Verify PSC = 79 and ARR = 999. Set the other two CCR registers to zero while testing one colour.
  3. Change CCR1, then CCR2, then CCR3. Watch the corresponding colour change even though the CPU is paused.

Check the debugger's number base. 500 decimal is 0x1F4. With ARR = 999, CCR = 999 is 99.9%; CCR = 1000 gives true 100%. The handout's ARR-as-maximum statement is inaccurate for this mode.

The supplied startup unfreezes TIM1. If CCR changes have no effect while paused, check DBGMCU → APB2FZ → DBG_TIM1_STOP = 0. With compare preload enabled, the running timer applies changes at its next update.

06

Measure your colour balance

The answers depend on your LED, not on a universal RGB ratio.

  1. Compare colours one at a time at the same CCR. Record strongest/weakest in answers 5–6.
  2. Set the strongest colour to a modest reference brightness, e.g. CCR = 200. Find CCR values for the other colours that look equally bright. Lower the reference if a colour cannot match it.
  3. Divide each matching CCR by the largest matching CCR. Put those three factors, in R/G/B order, into led.SetBalance(...) in Run.cpp.

Example only: matching values R = 400, G = 200, B = 500 would give led.SetBalance(0.8f, 0.4f, 1.f);. Use your own observed values.

07
Required task 2

Enable smooth colour cycling

  1. Stop Debug. In TIM1 → NVIC Settings, enable TIM1 update interrupt and TIM16 global interrupt. This is TIM1_UP_TIM16_IRQn on your L433; the handout's TIM10 screenshot is for another MCU.
  2. Generate code. Verify TIM1_UP_TIM16_IRQHandler() calls HAL_TIM_IRQHandler(&htim1);. TIM16 itself need not be started.
  3. Set color_cycle_enabled = true in Run.cpp. Keep freq = 0.2f initially and keep your measured balance factors.
  4. Build and run. The colour pattern should repeat roughly every 5 seconds. Changing freq to 0.5 gives a 2-second cycle; PWM stays at 1 kHz.
TIM1 update every 1 ms→ISR: increment counter→Main: sine + balance + CCR

The supplied Run calls HAL_TIM_PWM_Start() for each channel, then HAL_TIM_Base_Start_IT() for update interrupts. Do not replace these with PWM compare interrupts. No sine, LCD or delay work belongs in the ISR.

Why the class counts interrupts

At 1 kHz, one update is 0.001 seconds. ColorCycle reads a monotonic interrupt counter and advances phase by the number of elapsed periods, so a temporarily busy main loop does not slow the animation. It also wraps phase instead of letting a floating-point time variable grow forever. Hardware PWM runs independently between updates.
